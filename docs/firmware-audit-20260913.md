# Аудит VT-STREET-M2 + T99W175 перед следующей сборкой

Дата: 13 сентября 2026. Проверенная [версия репозитория](https://github.com/makssbaks/vt-street-m2-openwrt/tree/5a3df165b8fdbafee1962c2fb39a1080a25772ab): `5a3df165b8fdbafee1962c2fb39a1080a25772ab` (`integration/web-20260913`).

## Вывод

Перед следующей полной сборкой следует исправить обработку незавершённых AT-команд, состояние QMI при ошибках и исчезновении USB, длительные операции SMS и повторное удаление сообщений. Затем добавить постоянный учёт трафика и режим настройки антенны. Обычные сценарии на роутере уже работали; приведённые ниже ошибки относятся главным образом к отказам, таймаутам и частично завершённым операциям.

Этот документ фиксирует аудит и предложения. Исправления в рабочие исходники, установка пакетов, изменения радио, сборка и прошивка во время аудита не выполнялись.

## Область проверки и доказательства

Проверены все 74 отслеживаемых файла нашего репозитория: C helpers с фактически применяемыми патчами, QMI/netifd и USB-скрипты, RPC/ucode, LuCI, ACL/menu, DTS/profile, состав пакета, конфигурация, тесты, установщики, упаковщики и оба workflow. Локальные исходники сверены с Git blob SHA указанной версии. Ядро Linux и все сторонние OpenWrt-пакеты не проходили отдельный построчный аудит; их исходники проверялись адресно для выяснения зависимостей и поведения netifd/сборки.

- Все 12 существующих JS/ucode наборов прошли на host-интерпретаторе из исходников build49.
- 19 изолированных сценариев startup helper и 8 сценариев проверки содержимого rootfs прошли.
- Фактически собираемые C helpers получены применением патчей `010-vt-sms-segmentation-and-alpha-sender.patch` и `020-vt-sms-shared-flock.patch`. Дополнительные предупреждения компилятора не выявили проблем.
- ASan/UBSan и 100 000 случайных PDU не выявили ошибок доступа к памяти в этих пробах; это не доказывает отсутствие всех ошибок. LeakSanitizer отключён из-за ограничения среды.
- Ошибки AT/SMS воспроизведены локальными socket/PTY-моделями; сбой QMI — подменёнными функциями qmicli/netifd; ошибки UI — моделями RPC/DOM; MAC и uImage — изолированными входными данными.
- Модему, SIM и действующему соединению тестовые команды не отправлялись.

## Ошибки, которые нужно исправить

### A01. QMI сообщает UP до успешного получения адреса — высокий приоритет

Место: `package/vtmodem/files/lib/netifd/proto/t99w175qmi.sh`, `proto_t99w175qmi_setup()`, строки 200–227 и 247–275.

Сначала отправляется `proto_send_update` с `up=1` и CID/PDH, а затем запрашиваются IP-настройки. При отсутствии IPv4-адреса останавливается только IPv4 bearer и возвращается ошибка. Ранее отправленный UP не отменяется. При IPv6 пустые настройки вообще приводят к завершению без ошибки; при dual stack может остаться выделенный IPv6 bearer.

Воспроизведённый порядок:

```text
IPv4: allocate/start → SEND_UPDATE up=1 → settings empty → STOP cid4 → NO_ADDRESS → exit1
IPv6: allocate/start → SEND_UPDATE up=1 → settings empty → exit0
Dual: start cid4 + cid6 → UP → IPv4 settings empty → STOP cid4 → exit1; cid6 не освобождён
```

Проверка [закреплённого netifd](https://github.com/openwrt/netifd/blob/cbb83a1857407a28a63dc09412a1f209195914ef/proto-shell.c) показала: код возврата setup после уже принятого UP сам по себе не возвращает интерфейс в DOWN. Исправить транзакционность setup: проверить пригодность настроек до окончательного UP, освобождать все созданные ресурсы на каждой ветке ошибки, явно сообщать правильное состояние. Добавить тесты реального QMI setup/teardown, а не только startup helper.

### A02. Не хватает обработки исчезновения модема и потери сессии — высокий приоритет

Место: `t99w175qmi.sh` (`init_config`), `etc/hotplug.d/usb/03_t99w175` (ветка remove), `usr/libexec/t99w175-net-ready` (ранний выход при UP).

Протокол устанавливает `no_device=1`, не включает `teardown_on_l3_link_down`, не запускает монитор состояния WDS. USB remove удаляет alias/ready, но не закрывает сетевую сессию через netifd. При новом появлении устройства helper может принять старый UP за действующее соединение и не восстановить новый bearer. Вывод основан на исходниках и проверке обработки LINK_DOWN в закреплённом netifd; реальный USB-цикл этим аудитом не выполнялся.

Поведение LINK_DOWN проверено по [точному исходнику netifd](https://github.com/openwrt/netifd/blob/cbb83a1857407a28a63dc09412a1f209195914ef/interface.c). Исправить передачу событий DOWN/availability, очистку ресурсов и восстановление сессии. Сохранять смысл ручной кнопки «Остановить»: повторное появление USB не должно отменять решение пользователя. Дополнительно устранить окно между чтением `autostart=true` и последующим `ubus up`.

Контроль WDS/USB следует отделить от проверки внешнего интернета. Один неудачный ping при фильтрации ICMP или ограничениях оператора не является основанием для перезапуска модема.

### A03. Неполный ответ AT принимается за успех — высокий приоритет

Место: `package/vtmodem/src/vt-at.c`, `transact()`; `src/vt-sms.c`, `read_until()`, `at_cmd()`, `delete_sms()`.

В `vt-at` любой непустой накопленный ответ при истечении срока превращается в успешный результат. В SMS частичный ответ с кодом `1` также преобразуется в успех.

Подтверждено:

```text
Ответ ^SLMODE:1,2 без конечного OK → transact_rc=0
Удаление CMGD, только постороннее +UNRELATED:1 без OK → at_cmd_rc=0
```

Это позволяет сообщить об удалении SMS без подтверждения модема. Требовать полный конечный результат; различать подтверждённый OK, modem error, timeout и обрезанный ответ. Записывающую команду после неоднозначного результата автоматически не повторять.

### A04. Общий AT lock и длительные RPC не имеют сквозного срока — высокий приоритет

Место: `vt-at.c`, `acquire_lock()`/`write_all()`; применяемый SMS patch `020-vt-sms-shared-flock.patch`; RPC `usr/share/rpcd/ucode/vtmodem`, `command()`, `common_status()`, `sms_call()`.

Блокирующий `flock` выполняется до таймера AT-команды. `write_all()` повторяет EAGAIN без общего срока. В изолированной проверке `vt-at -t 100` оставался на lock дольше 500 мс и вышел только после его освобождения.

Status делает 13 синхронных общих AT-запросов плюс отдельный helper. При медленных ответах суммарное время может превысить минуту, при lock ожидание не ограничено. Отправка SMS допускает до 60 секунд на часть. Браузер может уже показать timeout, когда операция на модеме ещё продолжается. Гарантия одного frontend-запроса не ограничивает число оставшихся backend-процессов.

Нужны единый monotonic deadline для lock/write/read, один сборщик телеметрии с кэшем и возрастом каждого источника, быстрый RPC чтения кэша. Статические сведения модема не нужно перечитывать при каждом обновлении сигнала. Длительные SMS лучше выполнять как задания с ID, прогрессом и отдельным получением окончательного результата.

### A05. Повтор частичного удаления использует устаревшие SMS ID — приоритет перед выпуском

Место: `www/luci-static/resources/view/vtmodem/sms.js`, обработчик удаления, строки 288–306.

Воспроизведено: удаление частей `[5,6]` успешно удаляет 5 и падает на 6; повтор снова вызывает `[5,6]`. Если модем к этому времени назначил номер 5 новому SMS, повтор может удалить уже другое сообщение. Переиспользование слота — условие риска, а не зарегистрированный случай потери SMS у пользователя.

После частичного сбоя блокировать действия над старым списком до нового чтения. На backend перед удалением желательно сверять идентичность сообщения, а не полагаться только на номер слота.

### A06. При частичной отправке SMS нет точного результата — средний приоритет

Место: `src/vt-sms.c`, `send_sms()`; RPC `sms_call()`; `sms.js`, отправка.

Искусственный PTY подтвердил: первый сегмент принят с `+CMGS/OK`, второй получает `+CMS ERROR`; программа возвращает только `{"ok":false,"error":"SMS send failed"}`. Число уже принятых частей теряется. Повтор всего сообщения может создать дубли; timeout после передачи текста оставляет результат последней части неизвестным.

Возвращать общее число частей, число подтверждённых, номер проблемной части и признак неопределённого результата. Не выдавать таймаут браузера за доказательство, что ничего не отправлено.

### A07. Повреждённый PDU может испортить разбор следующего SMS — средний приоритет

Место: `src/vt-sms.c`, `decode_gsm_text()`, `parse_udh()`, `list_sms()`.

Подтверждено: один байт текста при заявленных пяти GSM septet превращается в `A@@@@`, вместо ошибки длины. Повреждённый multipart PDU успевает записать concat-поля, после неудачи структура переиспользуется; следующее обычное SMS наследует эти поля и может ошибочно участвовать в склейке.

Каждое сообщение разбирать в отдельной обнулённой структуре, переносить результат только после полного успеха. Проверять UDL/UDH, доступное число бит и корректность Unicode. Разрезание GSM escape-пары в фактическом C-кодировщике уже исправлено патчем 010 — это не новая найденная ошибка.

### A08. Два дефекта формы SMS — средний/низкий приоритет

Место: `sms.js`, строки 150–156 и 223–232.

- Во время отправки можно набрать новый текст, но завершение предыдущей отправки безусловно очищает поле. Новый черновик теряется. Очищать только неизменившийся отправленный текст либо фиксировать поле на время операции.
- Оценка частей не повторяет реальные правила кодировщика. `152 × a + 77 × ^` и `66 × я + 34 × 😀` показывают две части, хотя кодировщик создаёт три из-за неделимых escape/surrogate-пар. Синхронизировать расчёт с C-кодом и проверить границы.

### A09. Обновление может перезаписать пользовательский LAN MAC — средний приоритет

Место: `etc/uci-defaults/20-vt-mac`, `set_bridge_mac()` и основная ветка.

При пустом Factory скрипт нового образа вычисляет MAC из USB serial модема и перезаписывает UCI без проверки ранее выбранного MAC. Изолированный тест подтвердил игнорирование существующего адреса. С тем же модемом автоматически вычисленное значение останется тем же; риск касается пользовательского MAC, замены модема и сохранённых настроек после обновления.

Сохранять валидные существующие значения, создавать fallback только при необходимости. Для варианта L860 с пустым Factory этот T99-специфичный fallback также не решает задачу.

### A10. Проверка uImage неполна — средний приоритет проверки сборки

Место: `scripts/collect-and-validate.sh`, Python-разбор uImage.

Текущая проверка пропускает искусственный 64-байтовый заголовок с правильным magic, неверной архитектурой, нулевыми CRC и заявленным payload 99 999 999 байт без самого payload. Это подтверждённый пробел проверки, не свидетельство повреждения текущей прошивки.

Добавить header/data CRC, сопоставление длины с реальными байтами, ожидаемые Linux/MIPS/kernel/compression и адреса загрузки/входа. Также проверять `supported_devices`, точный состав sysupgrade и NAND upgrade handler внутри извлечённого образа, а не только в исходном дереве.

### A11. Старый упаковщик телеметрии теперь собирает смешанный пакет — средний приоритет сопровождения

Место: `scripts/package-t99-telemetry.py` и `scripts/install-t99-telemetry.sh`.

При запуске на нынешней ветке упаковщик берёт уже обновлённый RPC с Radio-методами, но не включает нужные для них launcher/control helpers/ACL/menu. Manifest и отдельные тесты такого архива могут пройти. Проверенные ранее выданные ZIP и состав полного firmware-пакета от этого не меняются.

Заморозить исторические упаковщики на известных версиях либо заменить единым версионируемым комплектом с полной проверкой зависимостей. Не пересобирать старые r1/r4 под тем же именем из произвольного текущего дерева.

### A12. Ошибка согласования Raw IP скрывается — средний приоритет

Место: `t99w175qmi.sh`, `qmi_enable_raw_ip()`, строки 81–91.

Ошибка `--wda-set-data-format` игнорируется; при отсутствии или недоступности sysfs `qmi/raw_ip` функция также может вернуть успех. Изолированная проверка реальной функции с ошибкой QMI и отсутствующим sysfs дала exit 0. Подтверждать фактически согласованный формат модема и драйвера. Неподдерживаемую WDA-команду допустимо игнорировать только после проверки, что формат уже правильный; иначе сообщать RAW_IP_FAILED.

### A13. Отмена setup и cleanup не охватывают все CID — средний приоритет

Место: `t99w175qmi.sh`, строки 170–210, 278–289.

CID до публикации UP хранятся только в локальных переменных setup. При отмене на промежуточном шаге teardown читает прежний `status.data` и может не знать о созданном bearer. Его несколько последовательных QMI/ubus-вызовов также не ограничены единым бюджетом, тогда как netifd ограничивает abort/teardown. Сохранять владение ресурсами сразу, учитывать поколение USB-устройства и делать идемпотентную ограниченную очистку. Это особенно важно при Stop во время подключения; не применять старый CID к вновь появившемуся модему.

### A14. USB hotplug может изменить выбранную firewall-зону — средний приоритет

Место: `etc/hotplug.d/usb/03_t99w175`, строки 145–164.

На каждом USB-ready event скрипт добавляет modem в WAN, даже если существующий интерфейс пользователь перенёс в другую зону. Поиск также предполагает анонимное имя `@zone[N]` и пропускает именованные UCI-секции. Назначать WAN только при первоначальном создании конфигурации, учитывать существующую принадлежность любой зоне и поддерживать оба вида секций. Для текущей стандартной WAN-зоны это не показанная неисправность.

Дополнительные ограничения QMI: время регистрации считается итерациями, а не общим временем вместе с запросами; credentials с пробелами/кавычками требуют корректного кодирования внутреннего key=value синтаксиса qmicli; обнаружение портов нужно целиком привязать к одному USB-устройству для будущей работы с несколькими модемами. Это не обнаруженная shell-инъекция и не текущая проблема APN internet без авторизации.

## Счётчик трафика в ГБ

В нашем VT Modem сейчас нет постоянного учёта трафика. Обычные счётчики RX/TX на странице Interfaces полезны, но не заменяют историю после пересоздания USB-интерфейса и перезагрузки.

Предлагаемый интерфейс:

| Период | Принято | Передано | Всего |
| --- | --- | --- | --- |
| Сегодня | ГБ | ГБ | ГБ |
| Текущий месяц | ГБ | ГБ | ГБ |
| С начала учёта | ГБ | ГБ | ГБ |

Дополнительно: текущая скорость приёма/передачи в Мбит/с, график по дням, выбранная дата начала расчётного месяца, ручной сброс с подтверждением. Единицы подписывать точно: 1 ГБ = 1 000 000 000 байт; GiB не выдавать за десятичный ГБ.

Рекомендую готовый `vnstat2` для хранения истории и небольшой блок в VT Modem для вывода. Пакет присутствует в ветке OpenWrt 25.12; отдельный `luci-app-vnstat2` тоже существует, но для нашей страницы можно использовать JSON vnStat без дополнительного PNG-интерфейса. Источники: [пакет vnstat2](https://github.com/openwrt/packages/blob/openwrt-25.12/net/vnstat2/Makefile), [LuCI-пакет](https://github.com/openwrt/luci/blob/openwrt-25.12/applications/luci-app-vnstat2/Makefile).

Источник объёма — RX/TX фактического интерфейса модема (`wwan0` в текущей конфигурации), не сумма LAN и WAN. Чтение статистики Linux не требует AT-команд; быстрые графики следует обновлять отдельно от медленной телеметрии. Данные интерфейса не гарантируют совпадения с тарификацией оператора. [Документация Linux](https://docs.kernel.org/networking/statistics.html).

Базу нужно разместить на постоянном разделе и включить в резервное копирование: путь под `/tmp` либо обычным временным `/var` историю не сохранит. Частоту записи выбрать отдельно от частоты чтения, например сохранять каждые 5–15 минут и при штатной остановке; при внезапной потере питания несохранённый интервал может потеряться. Учесть синхронизацию часов, пропадание/возврат интерфейса и сброс его счётчиков. Это поддерживаемые механизмы vnStat, но интеграционные сценарии нужно проверить на роутере. [Параметры vnStat](https://humdi.net/vnstat/man/vnstat.conf.html), [поведение daemon](https://humdi.net/vnstat/man/vnstatd.html).

## Улучшение связи

По последнему пользовательскому снимку: LTE B3 + B1, RSRP примерно −108 dBm, RSRQ −17 dB, SNR 3,6 dB. Это повод работать над приёмом и качеством канала. Сильный RSSI сам по себе не гарантирует хорошую связь; приведённые пороги производителей служат ориентиром, не гарантией скорости конкретного T99. [Пояснения параметров и рекомендации по расположению антенны](https://wiki.teltonika-networks.com/view/Mobile_Signal_Strength_Recommendations).

В прошивку полезно добавить режим «Настройка антенны»: крупные показатели, графики RSRP/RSRQ/SNR, текущие band/cell, сравнение сохранённых замеров при разных направлениях. Частый сбор должен идти через единый ограниченный сборщик после исправления A04. Сравнение сот/диапазонов оформлять отдельными действиями с сохранением исходных настроек; изменения могут временно прерывать интернет.

Физическое улучшение зависит от подходящей антенны, её ориентации/места, соединений и потерь в кабеле. Код OpenWrt не добавляет усиление приёмной антенне. Без модели новой антенны, схемы подключения и длины/типа кабелей нельзя обоснованно рекомендовать покупку или обещать прибавку сигнала. Повышение мощности передатчика не является способом повышения чувствительности приёмника.

RX3/RX4 = −140 dBm на снимке нельзя считать доказательством неисправности двух антенн. Сейчас парсер отбрасывает `rx_diversity` и показывает значение −140 буквально. Нужно сохранить исходный признак, выяснить его семантику именно в GC.004 и затем разделять измеренное значение, отсутствие данных и неактивный тракт. Автоматически скрывать любое −140 без этого также неверно.

## Другие полезные доработки

1. Журнал событий модема: пропадание USB, потеря регистрации, причины QMI-ошибок, восстановление и время простоя. Кнопка выгрузки диагностики с исключением паролей и маскировкой SIM/IMEI по умолчанию.
2. Версия нашей сборки в интерфейсе: номер build, commit проекта и release vtmodem. Сейчас OpenWrt revision не описывает установленный набор hotfix.
3. Закрепить commit всех feeds. Сейчас OpenWrt закреплён, а LuCI/packages и остальные feeds двигаются; сборка не полностью воспроизводима. [Конфигурация исходного OpenWrt](https://github.com/openwrt/openwrt/blob/6c40bc0bb0e78c67a1f7d8e6d4b048e78951b932/feeds.conf.default).
4. Запускать быстрые проверки на PR отдельно от длительной компиляции. Включить регрессионные тесты C-транспорта и настоящего QMI setup/teardown, которых не было в текущем наборе.
5. Корректное сохранение конфигурации/статистики и документированное восстановление после неудачного обновления. Фактический bootloader recovery отдельно не проверен.
6. SIM PIN и выбор PDP — будущие возможности. Для нынешней SIM READY и IPv4 они не требуются; IPv6/dual-stack сначала нуждаются в исправлении A01 и проверке на операторе.
7. Полная 5G-телеметрия и дальнейшая проверка L860 — отдельный этап, если эти режимы потребуются. Сейчас подробные radio/cell-поля разбираются преимущественно для LTE.

## Что исправлять не требуется по результатам этого аудита

Разметка NAND и лимит kernel 4 МиБ соответствуют предоставленным аппаратным логам. U-Boot и Factory в DTS помечены read-only. Все установленные новые runtime-файлы включены в Makefile; подтверждённой отсутствующей зависимости пакета не найдено. В просмотренном RPC/LuCI коде не найден конкретный XSS, shell-RCE или обход подтверждения Radio. Это границы текущего аудита, а не бессрочная гарантия безопасности.

## Порядок работ

1. Исправить QMI/AT/блокировки/удаление (A01–A05, A12–A14), затем ошибки частичных SMS/PDU/черновика. Для каждой добавить воспроизводящий тест.
2. Исправить сохранение MAC и проверки готового образа, закрепить зависимости и убрать неоднозначность исторических пакетов.
3. Добавить vnStat-учёт трафика и вывести ГБ/скорость/историю в VT Modem.
4. Добавить режим настройки антенны и журнал связи.
5. Пройти локальные регрессионные тесты, короткие проверки на устройстве по одному шагу, затем собрать и проверить единый образ.

Нынешний рабочий роутер этим аудитом не изменялся. Реальные переключения диапазонов/режима/фиксации соты по-прежнему не подтверждены аппаратной проверкой; ранее подтверждалось применение уже выбранного значения.
